# Fortis Ecosystem — Deployment Guide

Production setup for a single-user Linux laptop plus one Android phone. Step-by-step first-time setup is in the [Installation Guide](../installation/README.md); this page is the reference for each deployed piece.

---

## 1. fortis-agent (systemd user service)

The agent runs as **your user**, never as root. One instance per user.

`backend/fortis-agent/systemd/fortis-agent.service`:

```ini
[Unit]
Description=Fortis Agent
After=network-online.target tailscaled.service
Wants=network-online.target

[Service]
Type=simple
ExecStart=%h/.local/bin/fortis-agent
Restart=on-failure
RestartSec=5s
Environment=RUST_LOG=info

# Hardening
NoNewPrivileges=yes
LockPersonality=yes
RestrictRealtime=yes
RestrictSUIDSGID=yes
MemoryDenyWriteExecute=yes
LimitCORE=0
UMask=0077

[Install]
WantedBy=default.target
```

- No secrets in the unit file. The token and identity key are generated by the agent into `~/.config/fortis/` (security §7.1).
- `LimitCORE=0` plus `PR_SET_DUMPABLE=0` in the agent keep key material out of core dumps.

```bash
systemctl --user daemon-reload
systemctl --user enable --now fortis-agent
journalctl --user -u fortis-agent -f
```

To keep the agent running when you're not logged in to a graphical session (so `sudo` over SSH can still be approved): `sudo loginctl enable-linger $USER`.

### Configuration

`~/.config/fortis/agent.toml` — full reference in [Architecture §3.2](../architecture/README.md#32-configuration-configfortisagenttoml). After editing: `systemctl --user restart fortis-agent`.

### Rotating the desktop token

```bash
rm ~/.config/fortis/agent.token
systemctl --user restart fortis-agent      # a new token is generated
```

Restart fortis-desktop afterwards.

## 2. pam_fortis

Never hand-edit PAM files for Fortis. The steps below follow the lockout safeguards in security §4.7.

### 1. Install the module file

```bash
cd backend
cargo build --release -p fortis-pam
# Debian/Ubuntu (multiarch directory — /usr/lib/security is NOT searched):
sudo install -o root -g root -m 0644 target/release/libfortis_pam.so /usr/lib/x86_64-linux-gnu/security/pam_fortis.so
# Fedora:
# sudo install -o root -g root -m 0644 target/release/libfortis_pam.so /usr/lib64/security/pam_fortis.so
```

### 2. Trust your phone

```bash
sudo fortis pam-enroll
```

Writes `/etc/fortis/pam/<user>.json` (root:root `0644`, directories `0755`). Re-run it after pairing or revoking a phone.

### 3. Test without touching sudo

```bash
sudo fortis pam-install        # writes /etc/pam.d/fortis-test only
sudo fortis pam-test           # approve on the phone → "PASS"; deny/wait → falls through to pam_deny ("FALLBACK OK")
```

### 4. Enable for sudo

Open a second terminal and run `sudo -s` there first (keep it open). Then:

```bash
sudo fortis pam-install --sudo
sudo -k && sudo true           # in a NEW terminal: phone prompt; deny it → normal password prompt
```

`pam-install --sudo` backs up the file to `/etc/pam.d/sudo.fortis-backup`, inserts exactly one line, and verifies the result:

```text
-auth   sufficient    pam_fortis.so
```

Optional module arguments:

| Argument | Default | Meaning |
|---|---|---|
| `timeout=<secs>` | `30` | Max wait for the phone (1–60). The agent's own `auth.approval_timeout_secs` should be equal or lower. The module's hard deadline is `timeout + 2 s`. |
| `services=<a,b>` | `sudo,sudo-i` | PAM services the module acts for; any other service → `PAM_IGNORE` immediately |
| `debug` | off | Log decisions (never secrets) to syslog (`sudo journalctl -g pam_fortis`) |

Behaviour (security §4.6): returns `PAM_SUCCESS` only for a valid phone signature; everything else is `PAM_IGNORE`, so the next line (your password) runs. Do **not** add `pam_fortis` to `login`, `sshd`, `gdm`/`sddm` or `common-auth`.

### Roll back

```bash
sudo fortis pam-uninstall          # removes the line and the test service, with the same checks
# If sudo itself is broken, use pkexec (separate PAM service, never touched by Fortis):
pkexec fortis pam-uninstall
pkexec cp /etc/pam.d/sudo.fortis-backup /etc/pam.d/sudo
```

### Revoke a lost phone

```bash
fortis devices list
fortis devices revoke <device_id>
sudo fortis pam-enroll          # removes it from the root-owned trust file
```

## 3. fortis-desktop

```bash
cd desktop
npm ci
npm run tauri build
# .deb:      src-tauri/target/release/bundle/deb/
# AppImage:  src-tauri/target/release/bundle/appimage/
```

The desktop app has no build-time dependency on `fortis-backend`; it only needs a running agent.

Tauri security settings that must stay in place: a strict CSP (`default-src 'self'`, no remote scripts or fonts), no `withGlobalTauri`, and only the app's own commands in `capabilities/default.json`.

## 4. fortis-mobile

```bash
cd mobile/android
./gradlew assembleRelease        # needs a signing config in ~/.gradle/gradle.properties
adb install app/build/outputs/apk/release/app-release.apk
```

The Termux backup CLI is installed separately on the phone with `bash mobile/cli/install.sh` inside Termux (see the [Installation Guide](../installation/README.md#off-site-copy-to-the-phone-optional)).

The native library comes from `backend/fortis-bindings` — see [Development §5](../development/README.md#5-fortis-mobile-and-fortis-bindings).

Phone settings for reliable `sudo` prompts:

- Notifications allowed for Fortis, including full-screen intents.
- Battery: **Unrestricted** for Fortis and Tailscale.
- Tailscale: Always-on VPN.

## 5. fortis-backup

User-level systemd timer, daily at 23:45, catches up after downtime (`Persistent=true`).

```bash
cd backup
cp backup.conf.example backup.conf && chmod 600 backup.conf
install -Dm644 systemd/fortis-backup.service ~/.config/systemd/user/
install -Dm644 systemd/fortis-backup.timer   ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now fortis-backup.timer
```

- `ExecStart` in the service is `%h/dev/Fortis/fortis-ecosystem/backup/fortis-backup.sh`; change it if you cloned elsewhere. Set the same path as `backup.script` in `agent.toml`.
- `ExecStartPre=/usr/bin/mountpoint -q /mnt/FortisVault` skips the run if the drive isn't mounted.
- `backup.conf` is read from the script's own directory and must be owned by you and not group/world-writable.
- Add `~/.local/share/fortis` to `SECRETS` so the (encrypted) vault is backed up.
- Phone push: when the phone isn't ready, the script runs `fortis backup ask-phone` (a **Backup waiting** notification on the phone; tap it) every 5 minutes, plus a desktop `notify-send`, and waits up to `MOBILE_WAIT_MINUTES` (default 15) in `backup.conf`.

Exit codes: `0` ok, `1` config, `2` mirror failure, `3` snapshot failure, `4` destination missing, `5` already running, `6` local ok but phone push failed.

## 6. Tailscale

- Laptop and phone in the same tailnet; phone on Always-on VPN.
- Recommended ACL: allow only your phone to reach the laptop on `tcp:8023`, and the laptop to reach the phone on `tcp:8022` (Termux sshd).

```json
{
  "acls": [
    { "action": "accept", "src": ["tag:fortis-phone"],  "dst": ["tag:fortis-laptop:8023"] },
    { "action": "accept", "src": ["tag:fortis-laptop"], "dst": ["tag:fortis-phone:8022"] }
  ]
}
```

## 7. Health checks

```bash
systemctl --user is-active fortis-agent
fortis status
ss -tlnp | grep 8023                          # only 127.0.0.1 and 100.x.y.z
ls -la /run/user/$(id -u)/fortis/             # agent.sock, 0600
stat -c '%a %U %n' ~/.config/fortis/* ~/.local/share/fortis/*
sudo stat -c '%a %U %n' /etc/fortis/pam/*.json
systemctl --user list-timers | grep fortis-backup
tail -20 /mnt/FortisVault/Logs/mirror/mirror.log
```

journalctl --user -u fortis-agent -n 100
journalctl --user -u fortis-backup -n 100
